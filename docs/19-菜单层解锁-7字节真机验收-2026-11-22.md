## 二、两个根因（都是"看起来像失败"的陷阱）

### 根因 A · `R_AARCH64_RELATIVE` 的 addend 漏改

改造载荷时把 `.init_array[0]` 指向新入口 `0x1480`，但 `.rela.dyn` 里对应的
`R_AARCH64_RELATIVE` **addend 仍是旧地址 `0x1398`**。

⇒ glibc 在 `dlopen` 时按 addend 重定位，把入口**覆盖回已被清零的旧 blob** ⇒ `udf`/`SIGILL`
⇒ `SET_FILE` 秒抛 `GenericUsbException`。

**极易误判为「写通道被封」** —— 实际通道正常（诊断中 `SET_FILE` 返回 `res=0`）。

> 修正：构建脚本必须**同时**改 `.init_array` 与 `.rela.dyn` 的 addend。

### 根因 B · WBI（暖启动镜像）没清，冷启动白做

`nflasha5` 存有 **WBI（Warm Boot Image，快速启动镜像）**。WBI 有效时，冷启动
**从旧 RAM 快照恢复**，根本不会加载新的 `appFw.so` ⇒ 表现为"改完冷启动，什么都没变"。

**正确顺序：先清 WBI，再写字节，再冷启动。** 顺序做反 = 白做。

> 清 WBI 只写 sysfs 触发内核 drop，**不直接改分区**；清前留原值与恢复方案，
> 清后读回确认（512 B 全零）再继续。

### 实测顺序（一次成功的那次）

```
dry（零写入，验证链路）
  → land（真写 01×7，状态读回 00）
  → 首次冷启动：失败
  → 定位 WBI，清 WBI
  → 第二次冷启动：菜单出现连拍
```

## 四、复现要点（不含下发脚本）

1. **前提**：服务会话可用（[docs/01](01-session.md)）、`SET_FILE` 通道可用（[docs/07](07-jiritsu-breakthrough.md)）、
   载荷满足 ELF 五条铁律（[docs/15](15-payload-elf-rules.md)）。
2. **改字节**：7 处 `00→01`，**等长**，`.text` 零改动；派生库 sha 应为 `ab0333be…`。
3. **清 WBI**：确认 `nflasha5` 的 WBI 已失效并读回验证。
4. **写入**：经 `SET_FILE` 落盘到 `/usr/lib/appFw.so`，读回全量 sha 校验。
5. **冷启动**：拔电池 ≥30 s（热重启不算）。
6. **判据**：菜单出现「连拍:Hi+」+ Hi+/Hi 档位条 + 选中态。
7. **回滚**：反向 7 字节（`01→00`）→ 清 WBI → 冷启动；或写回原库 `72d9136f…`。
