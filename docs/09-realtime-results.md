> ILME-FX30 Ver.6.00 实机 + Type-C，两阶段认证通过。本文记录**实机观测**，与离线推导分开。
> 全部操作为**只读**（AdjustControl 请求一律空 payload 或只读 FileControl cmd=2）。

## 一、会话基础

| 项 | 结果 |
|---|---|
| 枚举 | `054C:0E0E`（MSC）→ 认证 → 重枚举 `054C:0336` |
| 两阶段认证 | ✅ 均成功 |
| `StopSenser` 之后 | ❌ 相机**从总线消失**，不会自动回 MSC，必须断电/拔插 |

## 二、`0xff01` FileControl —— 很可能未实现

| 测试 | 结果 |
|---|---|
| 21 组路径 × 填充变体（含 `/usr/lib/appFw.so`） | 全部 `128`（0x80）/ 0 字节 |
| 空文件名（`filenameSize=0`） | **也是 128** |
| 换 4 字节对齐 / PMCA 补零 | 128 |
| 干净会话复测（未被污染的端点） | 128 |

**判读**：响应**与路径完全无关**，连空文件名都返回同一码 → 请求在路径解析前被整体拒绝。结合 A6700 上同一写法可读 89 MB，判断 FX30 的 `0xff01` **很可能没有实现**（而非路径问题）。

## 三、`0xff03` MemoryDump —— 未通

| 测试 | 结果 |
|---|---|
| `base=0x0, size=0x100` | 128 |
| `base=0x100000, size=0x100` | 128 |

## 四、`category=0x1001`（Jiritsu）—— **存在**

同一次会话内、端点干净时，`0x1001` 稳定响应：

| 命令 | res | 返回 |
|---|---|---|
| `1, 2, 3, 4, 5, 9, 13, 18` | **0** | 4 字节 |
| **`4` / `5` / `13`** | **0** | **`18 00 00 10` / `23 00 00 10` / `06 00 00 10`**（非零，重复 3 次不变） |
| `14` | 0 | 空 |
| `6, 7, 8, 10, 11, 12, 15, 16, 17, 20` | **136**（0x88） | 空 |
| `19, 21–32` | 129 | 空 |
| `0x4001, 0x4002, 0x4003, 0x4009, 0x4012` | 0 | 4 字节 0 |
| **`0x4004` / `0x4005` / `0x400D`** | **0** | 与 `4/5/13` **完全相同** |
| `0x400E` | 0 | 空 |
| `0x4006–08, 0x400A–0C, 0x400F–11, 0x4014` | **136** | 空 |
| `0x4000, 0x4013, 0x4015–0x4020` | 129 | 空 |
| `category 0x1002` 全部 | 192 | 空 |

**两点结论**：

1. `0x1001` 是**真实存在**的命令类别，`res=0` 表示成功。
2. **`0x4000` 是模式位**：`cmd n` 与 `cmd 0x4000|n` 返回完全相同（验证于 4 / 5 / 13）。
3. `136` 是新的响应码（≠128「不存在」），含义应为「**命令存在，但缺少参数/状态不符**」。

## 五、端点脆弱性（重要）

| pFunc | 结果 |
|---|---|
| `0xff05` / `0x1234` | `GenericUsbException` |
| `0xff09` | 「错误的 senser 序列」 |

一旦发送未知 pFunc，**端点即被破坏**，同一会话后续请求全部异常。
→ **不要在一条会话里混测未知 pFunc**；先测关键项，未知项放最后或不测。

## 六、离线：`libJiritsu.so` 的命令处理函数

固件里同时存在 `libJiritsu.so`（233 KB）与 `libsencore.so`（381 KB）。`libJiritsu` 保留了完整的处理函数符号：

```
cmd_jiritsu_get_version      cmd_debug            cmd_mount
adj_cmd_get_file             adj_cmd_set_file     adj_cmd_set_file_path
adj_cmd_get_file2            adj_cmd_set_file2    cmd_file_delete
cmd_file_delete2             adj_cmd_get_file_list
adj_cmd_get_file_hash        adj_cmd_set_firm
cmd_high_capacity_get_file   cmd_high_capacity_send_file
adj_cmd_compare_media        cmd_mode / cmd_format / cmd_start / cmd_factory
```

即：**读、写、删、列表、哈希、固件写入** 全部具备。

**但数字命令号 → 处理函数的映射无法静态直读**：分发通过字符串接口 `"SenserCommandIf"` 在运行时解析，`libJiritsu` 没有把处理函数以绝对地址写进任何表（已核对 `.rela.dyn`、`.data.rel.ro`、`.text` 的 ADRP+ADD 与 BL）。

## 七、当前判断

| 项 | 结论 |
|---|---|
| `0xff01` / `0xff03` | 很可能未实现（实机一律 128，且与路径无关） |
| **`category=0x1001`** | **存在**，有完整文件命令处理函数 |
| 写通道 | **存在可能性高**，但需先确定「哪个命令号是 GET_FILE / SET_FILE」 |
| 数字→语义映射 | 需进一步离线分析或谨慎的参数探测 |

---

## 八、下一步（按风险从低到高）

1. **离线**：继续解析 `"SenserCommandIf"` 的名字注册表，把命令号与 `cmd_*` 对上（零风险）。
2. **谨慎探测**：对返回 136 的命令发送**无效 file_id**（如 `0xFE`）的 3 字节载荷，观察响应是否从 136 变化——可区分「读」与「写」，但有极小概率触碰真实文件。
3. **硬件兜底**：Pico / BootROM。

*本文只记录只读实测。任何写入型操作前，必须先有完整备份与官方 SD 恢复包。*
