# 14 · 跨机型通道互证：与上游研究者的公开对照

> 2026-10-24：在 [`xyzhangxin/sony-a6700-powerful`](https://github.com/xyzhangxin/sony-a6700-powerful) Issue #2 中，
> 该项目作者回复了本仓库的提问。本文把对方的具体说法与 FX30 Ver.6.00 的实测结果逐条对照。
>
> 结论先行：**骨干逐字节吻合，两处编号语义待定，一处对方留的空白由本方补上。**

---

## 一、背景

本仓库早期判断是「FX30 只有 `pFunc=0x40`，文件与内存通道都返回 128」。
同代机型（A6700 / A7C II）的公开工作显示：它们的写入**根本不依赖 `0xff01`/`0xff03`**，
而走 Senser 认证后的 Jiritsu 文件服务。本仓库据此重新测绘，证实 FX30 也走同一条路。

对方的回复给出了他们在 A6700 上的完整三步骤。下面是逐条对照。

---

## 二、四条同向（我方有 FX30 实机物证）

| # | 对方说法 | FX30 Ver.6.00 实测 | 判定 |
|---|---|---|---|
| 1 | 不走 `0xff03` MemoryDump，也不走 `0xff01` FileControl | 两者**全部返回 128**（含 `0xFFFF0000`） | ✅ 边界相同 |
| 2 | 走 Senser 认证后的 Jiritsu：`pFunc=0x40` / `category=0x1001` | 完全相同（`0x4001`–`0x4012`） | ✅ |
| 3 | 载荷前缀 `{area=0, file_id, transfer_mode=0}`，小端 | `payload = [0, 2, 0] + data` | ✅ **逐字节一致** |
| 4 | `0x4007 SET_FILE / file_id=2` 加载 `/tmp/jiritsu/libJit.so` | `res=0`，且读回自写副作用文件 | ✅ **已实证执行** |

第 4 条的实机记录：

```
[0] GET_VERSION 0x400D              -> res=0  len=4   06 00 00 10
[1] SET_FILE 0x4007 plen=10,187     -> res=0  len=4   00 00 00 00
[2] GET_FILE 0x4008 [0,3,0]         -> res=0  len=20  b'PWNED-JITLOG-V4\n'
```

返回值 `0x00000000` 是「写入成功 + `dlopen` 成功」的合取；
副作用文件由**自写的 ARM64 机器码**产生，不是主机侧回显。

另有一条同向：对方称「固定范围」**不是** `0x603/0x05` 的 BK4 设置区 ——
本仓库独立查明该 2,253,564 字节块是 CP/MP 芯片参数的备份副本，固件启动不从中恢复用户设置，
与对方判断一致（见 [`13-flash-layout.md`](13-flash-layout.md) §3）。

## 三、对方留的空白：FX30 6.00 已确认同构

对方原话：

> 上述加载路径仅在 A6700 2.00 验证，FX30 6.00 的加载行为和固件修改范围仍需单独确认，
> **不能直接套用 A6700 载荷**。

前半句是负责任的提醒，后半句是对的 —— 但结论应更新为「**已验证可用，但需自建载荷**」：

| 项 | 状态 |
|---|---|
| FX30 6.00 的 Jiritsu 加载链路 | ✅ **与 A6700 同构、可用** |
| 能否直接用 A6700 的载荷 | ❌ 不能（架构/符号/地址全不同） |
| 本仓库走的路 | 借壳本机 `libssp.so` 的 216 B 余量 → 后改为 zig 独立构造合法 `.so` |

zig 构建的 `libJit_stage1.so` = **2,192 B**，`PT_LOAD` 3 段无 W+X、
`PT_GNU_STACK flags=6`、`DT_INIT_ARRAY → R_AARCH64_RELATIVE`，
结构与相机原生 `libJiritsu.so` 对齐。**216 B 上限已解除。**

## 四、两处编号语义分歧（待实测）

### 4.1 `file_id` 槽位表（反汇编硬证据）

`libJiritsu.so` 的 `get_jiritsu_area_filename()` @ `0x1236C` 用跳转表实现，
字节 `1C 00 13 16 19`，目标 `0x8F2C + byte*4`：

| `file_id` | 路径 | 说明 |
|---|---|---|
| 0 | `/tmp/jiritsu/tmmc.jit` | 对方称之为「读取器配置」 |
| 1 | `/tmp/jiritsu/DIAC.csv` | 命令映射表本体（实测可读） |
| **2** | **`/tmp/jiritsu/libJit.so`** | **与对方 `file_id=2` 完全一致** |
| 3 | `/tmp/jiritsu/jit.log` | 本仓库用它做闭环验证 |
| 4 | `/tmp/jiritsu/history.txt` | 历史注入记录 |

`file_id > 4` 时改走 `0x470AD8` 的 34 项查找表（16 B/项 `{u8 id, pad, u64 path_ptr}`）。

`file_id=2` 一致，说明两边是同一套硬编码。

### 4.2 分歧点

| | 对方说法 | 本仓库判定 |
|---|---|---|
| `0x4010` | `SET_FILE_2`，`file_id=0` = **发送读取器配置**（流程第一步） | `SET_FILE2` = 配合 `0x400F SET_FILE_PATH` 的**按路径写** |
| `0x4008 file_id=0` | 取回「执行结果」 | `file_id=0` 是 `tmmc.jit`；本仓库用 `file_id=3`（`jit.log`）闭环 |

**这两说不一定冲突。** 若「读取器配置」真写在 `file_id=0`，按上表落点就是 `tmmc.jit` ——
即**对方口中的「读取器配置」很可能就是本仓库索引表里的 `tmmc.jit`**，同一件东西两种叫法。

至于「取回执行结果」用 0 号槽，只有两种可能：

- (a) 他们的载荷主动把结果写进 `tmmc.jit`（覆盖配置表）；
- (b) 记错了槽号。

本仓库实测 `file_id=3` 即可完成「执行 → 回读」闭环，**无需借用配置槽**。
FX30 上尚未发过 `0x4010`，此项待实测。

## 五、对方「260 扇区」的量纲含义

对方提到预检范围是 **260 扇区 / 133,xxx 字节**。

| 读法 | 算式 | 判读 |
|---|---|---|
| `260 × 512 = 133,120` | 整整齐齐 | 在按 512 B 扇区访问块设备 |
| `133,128 = 133,120 + 8` | 多 8 字节 | 扇区数据 + 8 字节头 |

不论哪一种，「260 扇区」这个量纲说明对方在 **块设备扇区层**操作。

**本仓库的旁证**：`0x603/6` status 报 PDT size = 2,253,052，
而 `0x603/5` 实读 2,253,564，差 **512** —— 正好一个扇区。这条链路本身也是扇区对齐搬运的。

### 三层能力矩阵

| 层次 | Powerful6700 | 本仓库 |
|---|---|---|
| 块设备扇区 | ✅ 260 扇区固定范围 | ❌ 未做 |
| 文件系统（路径） | 未知 | ✅ `0x400F`+`0x4011` 任意路径读，SHA-256 级验证 |
| 属性语义（BKID） | ❌ 「没有已验证的 ID」 | ✅ BKID 表 25,167 条 + 属性访问器表 2,692 条 id |

⇒ 这是**层次差异，不是对错**。扇区层说没有属性 ID，不等于语义层没有属性 ID；
反过来，语义层拿不到扇区位图。两层可以互补。

## 六、驱动模式：对方的「没有」是本仓库的「已有」

对方明确表示无法提供驱动模式的 BK4 属性 ID。
这不影响本仓库的结论 —— 因为双方定位手段不同：

| | 对方 | 本仓库 |
|---|---|---|
| 粒度 | 260 扇区盲区段 | 单个属性 ID + `.bss` 地址 |
| 目标区域 | 133 KB 量级 | **104 字节**（`0x8230D84`–`0x8230DEC`） |
| 驱动模式 ID | 无 | `BKID_APP_setting_drive_mode_cont_shooting` = **`0x04B8`（1208）** |

本仓库已有的相关事实（离线，三机型对照）：

- FX30 与 FX3 的 BKID id **逐位相同**；A6700/A7C2 是另一套编号——**分段位移**（`0x02B1` 族 +5、`0x04B8` 族 +1，见 `docs/11` §二）并多出 `HI_PLUS`；
- 两代建模差异：FX30/FX3 = **枚举 + 受限降级**（`CONT_SHOOTING_LIMITED_*` 后缀）；
  A6700/A7C2 = **限制原因枚举**（`DRIVE_MODE_LIMIT_CONTINUOUS_SHOOTING_*` 前缀）；
- 三轮「找开关」全部为负：FX30 固件里连拍的名字、列表、API 一个不缺，`.text` 比 FX3 还大 11,128 字节。

## 七、一条操作警示

`/tmp/jiritsu` 是 `/dev/nflasha6`（`nflasha6 = Jiritsu`，25 MB **flash 分区**）的真实挂载点。
通过 `SET_FILE / file_id=2` 写入的文件**跨重启保留，并会被固件反复 `dlopen`**。

⇒ 测试载荷用完**必须**用 `FILE_DELETE`（`0x4009` / `0x4012`）删除，
再用 `GET_FILE [0,2,0]` 读回确认为空。**不能靠断电清除。**

配套只读探针：[`tools/probe_fileid_map.py`](../tools/probe_fileid_map.py)
（只发 `GET_FILE`，逐槽读回核对上表；`0x4010` 需显式加 `--allow-4010`）。

## 八、方法论提炼

三条从这次对照里得到的通用规则：

1. **别人的「没有」，先问「他站在哪一层」。**
   不同层次的能力边界不能互相否定。
2. **能对上的最小单位是字节，不是概念。**
   「走 Jiritsu 文件服务」是概念；`[0, 2, 0] + data` 才是可核验的事实。
3. **对方留的空白比对方的结论更有价值。**
   「FX30 6.00 需单独确认」这一句，直接指出了本仓库最该做的那次实验。
