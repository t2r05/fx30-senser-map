# 属性访问器表：从设置 ID 到 `.bss` 地址

> 本文是全仓库**最硬的一环**：它把「设置 ID」翻译成「进程内存地址」，且不需要在相机上跑任何东西。
> 全部结论来自 `appFw.so`（**FX30 Ver.6.01 固件包**）的 `.data.rel.ro` 静态分析，无实机写入。

> 🔴 **地址层前提未验证（2026-10-24 审计）**：本文全部 `.bss` 地址是 **6.01 固件包**里的坐标。
> 机器 `GET_VERSION` 自报 6.00，而 `libJiritsu.so` 的 SHA 与 6.01 包一致（小库可能跨版本不变）。
> **`appFw.so` 是否同一份从未验证** —— 0.01 升级加一个全局变量就足以让其后所有地址漂移。
> 裁决实验（读回三段指纹）通过前，这些地址只能视为「包上的坐标」，不可直接用于实机写入。
> 详见 `audit/00-版本错配.md`。

## 一、表结构：0x58 字节/条

在 `.data.rel.ro` 里发现一张记录表，每条 `0x58` 字节：

```c
struct prop_record {          // 0x58 = 88 字节
    uint64_t id;              // +0x28   ← 不是 +0x00（2026-10-24 更正）
    void    *stub[8];         // +0x10 .. +0x48   ← 旧描述的偏移整体错 0x28
    uint64_t meta;            // +0x50
};
```

> 🔴 **2026-10-24 结构更正（详见 `fx30_hack/audit/10-属性表三代结构.md`）**
>
> 本文早期版本记「表基址 `0x0402EB48`，`+0x00` = id，`+0x08` = attach，`+0x10..+0x48` = 八个桩，`+0x50` = meta」。
> 实测真实基址是 **`0x0402EB20`**，`0x0402EB48 - 0x0402EB20 = 0x28` ——
> 旧版本把**第一条记录的 id 字段地址**当成了**记录起点**。
>
> 正确布局（`0x58` = 11 槽）：
>
> ```
> +0x00 .. +0x20   5 个访问器（.text）
> +0x28            u64 id
> +0x30 .. +0x50   5 个访问器（.text）
> ```
>
> 校验：FX30 首 6 条记录的 `+0x28` 恰好是 `0,1,2,3,4,5`；
> `0x02AF`/`0x04B8`/`0x04BA` 全部命中。
>
> **影响**：按 id 查表一直是对的（因为基址和偏移错等量），但「读那 8 个桩」读到的
> 其实是真实记录的 `+0x38..+0x70`，**跨了记录边界** —— 漏掉了 `+0x00` / `+0x08` / `+0x50` 三个桩。
> §三 表格因此不全，见下方补充。

每个桩（stub）只有 3–5 条指令，形如：

```arm64
adrp x8, <page>       ; 目标页
ldr  w0, [x8, #off]   ; 读  → .bss 变量
str  w1, [x8, #off]   ; 写  → .bss 变量
```

⇒ **桩体本身就编码了目标 `.bss` 地址**，不需执行、不需调试器。

扫描脚本：`map_prop_table.py <机型> [--dump=0xID,...]`
产物：`diff3_wb/prop_table_FX30.tsv`（**2,692 条**连续 id，`0x0000`–`0x151E`；全候选 4,426 条）

## 二、BKID 与属性表是同一套编号

`0x04B8`（`BKID_APP_setting_drive_mode_cont_shooting`）在同一张表里**有记录**：

```
## id 0x04B8  记录 0x04048A88
   stub[5]  ldr@0x831F848, str@0x89254F0     ← .bss → 镜像
   stub[6]  ldr@0x89254F0, str@0x8220304, str@0x8220308
```

⇒ 链路 **名称 → id → 记录 → `.bss` 地址** 四段全通。

## 三、连拍族的内存地址（FX30 6.00）

| 用途 | id | 主槽 | 处理副本 | 镜像 |
|---|---|---|---|---|
| `menu_drive_mode`（**字节**） | `0x02AF` | `0x8230D84` `0x8230D86` | `0x8220844` `0x8220845` | `0x8836A2C` |
| `dial_hi_in_electric_shutter` | `0x02B1` | `0x8230D98` `0x8230D9C` `0x8230DA0` | `0x8220858` `0x822085C` | `0x8836A44` |
| `dial_mid` | `0x02B3` | `0x8230DB8` `0x8230DC0` | `0x8220878` `0x822087C` | `0x8836A60` |
| `dial_lo` | `0x02B5` | `0x8230DD8` `0x8230DDA` | `0x8220898` `0x8220899` | `0x8836A80` |
| **`cont_shooting`** | **`0x04B8`** | **`0x831F844` `0x831F848` `0x831F84C`** | **`0x8220304` `0x8220308`** | **`0x89254F0`** |
| `cont_shooting_limited` | `0x04BA` | `0x831F868` `0x831F86C` `0x831F870` | `0x8220328` `0x822032C` | `0x8925514` |
| `registration_available0` | `0x0C2C` | `0x8346290` `0x8346294`、`0x83461A0` | `0x8220C60` `0x8220D50` | `0x894BF38` |
| `registration_available1` | `0x0C2D` | `0x83462A4` `0x83462A8`、`0x83461A4` | `0x8220C64` `0x8220D64` | `0x894BF4C` |

**全部在 `.bss`**——即 RAM 变量。

> ⚠️ **上表是按旧偏移（`+0x10` 起）读出来的，漏了 3 个桩。**
> 补全后（`+0x00` / `+0x08` / `+0x50` 三个访问器的目标）：
>
> | id | 补上的 `.bss` |
> |---|---|
> | `0x04B8` | **`0x831F82C`**（`+0x00` 纯 getter）、**`0x831F830`**（`+0x08` 读 `0x831F830` → 写 `0x89254D8`）、`0x831F858` `0x831F85C` `0x831F860`（`+0x50` 族） |
> | `0x04BA` | `0x831F87C` `0x831F880` `0x831F884` |
>
> `+0x20` 与 `+0x30` 是两个**返回常量的桩**：`mov x0, #4` / `mov w0, #1`（值的枚举基数或合法范围），
> 不对应任何 `.bss` 地址 —— 旧描述把它们当成「访问器桩」也是误读。
>
> 另：`0x04B8` 的 `+0x18` 桩返回的是**地址**（`adrp 0x8220000` + `#0x540` + `#0xff, lsl #12` + `#0x2f0` = `0x831F830`），
> 供上层做原地读写，不是取值。


> 注意：这不等于「不存在持久化副本」。`0x8EF80` 在 PDT 里且与驱动模式相关，
> 说明存在某条 RAM ↔ PDT 的同步路径（见 `docs/10` §五、`audit/02`）。

### 类型细节

`0x02AF`（`menu_drive_mode`）、`0x02B5`（`dial_lo`）用的是 **`ldrb`/`strb` 单字节**；
`0x02B1` / `0x04B8` 用的是 **`ldr`/`str` 32 位字**。

这个类型差异很重要：**「可用性字节」是单字节，在 `0x8230D84`。**

## 四、每条属性实为「三存储簇」

从 stub 的读写模式可以看出，同一个逻辑值在三个地方出现：

| 簇 | 位置 | 由哪个桩访问 | 作用 |
|---|---|---|---|
| **原始对** | `0x831F844`/`0x831F848`/`0x831F84C` | `stub[0..4]`（原生读写） | 值本体 |
| **处理三连** | `0x8220304`/`0x8220308` | `stub[6]`（从镜像转写） | 加工/缓存值 |
| **镜像** | `0x89254F0` | `stub[5]`（主槽 → 镜像） | 快照/回滚源 |

⇒ **假设（未验证）**：写入可能需要三处同步，否则被镜像回滚。
（该因果链目前只由桩的读写形态推断，从未实机验证；`docs/12` 原 §六 亦承认「同步顺序待验证」。）

这一条解释了一个此前反复出现的现象：早前在 PDT 文件里写进去的字节「保住了但行为不变」，以及在设置通道里出现的「写了又被归一化」——都是因为改的不是同一簇。

## 五、跨机型不通用 —— 实测是**三种不同布局**

> 🟢 **2026-10-24 已解**：不是「A6700/A7C2 不是 0x58 结构」这么模糊，而是**三代三种布局**。

| | FX30 6.01 | FX3 3.00 | A6700 2.00 | A7C2 2.01 |
|---|---|---|---|---|
| 表基址（vaddr） | `0x0402EB20` | `0x0402ADE8` | `0x04818040` | `0x0571A578` |
| stride | `0x58` | `0x58` | **`0x50`** | **`0x68`** |
| 槽数/条 | 11 | 11 | 10 | 13 |
| id 存放 | 记录内 `+0x28` | 记录内 `+0x28` | **无（下标即 id）** | **无（下标即 id）** |
| id 空间 | ~8192（**乱序交错**） | ~8192 | 7520 | 6570 |
| 记录首槽 | `.text` | `.text` | `.bss` | `.text` |

**为什么旧判据找不到 A6700 / A7C2**：`find_prop_table.py` 找的是「等距且**严格递增的 id 列**」，
这隐含「记录内有 id 且 id 连续」两个假设 —— 第二代两条都不满足。
换成「一条记录里串着若干 `.text` 函数指针」这个判据才通吃三代。

FX30 自身也不满足「严格递增」：它的 id 是**成对交错**的
（`0x2A`↔`0x2B` 互换，`0x66`↔`0x71`、`0x67`↔`0x70`、`0x68`↔`0x6F` 镜像递减）。
所以旧脚本在 FX30 上报的「最长连续 572 条」是**连续段长，不是表长**。

⚠️ **这条很重要**：任何「按 id 查 `.bss` 地址」的方案都必须**按机型重新建表**。
不仅基址不能复用，连 stride 和索引方式都不同。

> 现场教训：若把 FX30 的基址 `0x0402EB20` 直接套到 FX3 上，全部记录 `+0x28` 都读成 `.text` 地址（MISMATCH）。
> FX3 的 `.data.rel.ro` 起点比 FX30 低 `0x3D38`，基址必须同步下移。
> `.bss` 更不通用：FX30 `0x04B8` 在 `0x831F82C`，FX3 在 `0x831B824`。

## 六、这张表能做什么、不能做什么

| 能做 | 不能做 |
|---|---|
| 离线确定任意设置 id 的运行时地址 | 证明某个地址就是「门控真值」 |
| 区分字节宽度（`ldrb` vs `ldr`） | 绕过写入校验 |
| 定位同一逻辑值的三处副本 | 跨机型复用 |
| 判断某值是否 RAM-only（全在 `.bss`） | — |

**已知未解**：哪个槽真正跟随驱动模式变化、`0x04B8` 的合法值域、三处同步写的正确顺序——都需要实机验证。

## 七、与另一路的交叉印证

> ### ⚠️ 更正（2026-10-24）：本节两条推断均已被实机推翻
>
> 1. ~~**PTD 备份文件不是真值源**~~ —— **错**。
>    实机写入 `0x8EF80=0x01` + `0x91690=0x01`（成对）后，
>    **拔电池冷启动 → 相机进入连拍且能正常连拍**。
>    PDT **就是**启动真值源。原观察的失败原因：① 只写一个字段 ② 用热重启验证。
>    见 [`13-flash-layout.md`](13-flash-layout.md) §三 更正块。
> 2. `0x603/1` 属性表与模式无关这一条**仍然成立**，但**结论方向要改**：
>    不是「真值在内存里所以文件无用」，而是「**属性表根本不是驱动模式的载体**，
>    驱动模式走的是设置区（PDT）里的枚举索引字段」。
>    另注：`0x603` 有两套命令面，此前混为一谈 ——
>    `cat=0x1001/cmd=0x603` 对任何 id 都返回固定 `01 02 00 10`（是 ack 不是属性值），
>    `cat=0x0603/cmd=1` 下 BKID 族全 `res=129`。见 [`04-dead-ends.md`](04-dead-ends.md) §十四。
>
> ⇒ **运行时真值在 PDT 设置区的 `0x8EF80`/`0x91690` 两个枚举索引字段上**，
> 运行时加载进 `appFw` 内存后的副本另在别处 —— 但**不需要走「改内存」这条路**，
> 写文件就够了。
