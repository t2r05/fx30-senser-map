# 此路不通的记录

在 FX30 Ver.6.00 上**已实测排除**的方向，以及踩过的坑。记录下来是为了避免重复劳动——每一条都消耗了真实的试错时间。

---

## 一、文件通道：⚠️ 结论已撤回（原测试方式有误）

> **2026-10-23 更正：本节原始结论「文件通道不存在」不成立。**
> 原始测试把**文件路径字符串**当作 `0x603`（AdjustControl）的 payload 发送，而 FileControl 是**另一个 pFunc（`0xff01`）**，其载荷格式为：
>
> ```
> cmd(int16) + filenameSize(int16) + 文件名（补 \0 到 4 字节）
> cmd: 1=写  2=读  3=删
> 成功时 response == 1；0x80 (=128) 是错误码，不是「接口不存在」
> ```
>
> 所以当时看到的 `128` 既不是 FileControl 的响应，也不能证明接口缺失。**本条已从「死路」改为「待实机复测」**，复测脚本：`probe_filecontrol.py`。

原始记录（保留备查）：当时对下列路径逐个发送 `0x603` 请求，均返回 128：

```
/  /etc  /bin  /usr  /lib  /mnt  /opt  /tmp  /var  /proc
/sys  /home  /root  /data  /system  /vendor
/usr/lib/appFw.so      ← FireHydrant 在 A6700 上明示的正确文件
/usr/lib/appFW.so      ← A7C2 工具日志中的大小写写法
/usr/lib/libJit.so
/etc/ld.so.preload
/usr/lib/os-release
```

## 二、内存通道：未读到数据（128 语义待区分）

### `pFunc=0xff03`（MemoryDump）未读到数据（响应 128）

| 基地址 | 长度 | 结果 |
|---|---|---|
| `0xFFFF0000`（BootROM，ILCE-7M4-RE 文档地址） | `0x6000` | **128** |
| `0x00000000` | `0x1000` | **128** |
| `0xFE000000`（eSRAM） | `0x1000` | **128** |
| `0x400000000`（System RAM） | `0x1000` | 参数越界（`MemoryDumpHeader` 为 INT32） |

**结论**：上述地址按当前载荷均未读到数据。**但注意**：`pFunc=0xff03` 的 128 也可能是错误码（与 FileControl 的 `0x80` 同类），「命令不存在」与「地址/参数被拒」尚未区分。本条同样标注为**待复测**，不宜再作为「内存通道不存在」的定论。

## 三、服务模式终端不可用

`setTerminalEnable(True)` 后，`writeTerminal`（向 `epOut[1]=0x04` 写）**超时**：

```
libusb0-dll:err [_usb_reap_async] timeout error
```

- 端点确实存在：`epIn=[0x81,0x83]`，`epOut=[0x02,0x04]`（均为 bulk 512）
- 注意：PMCA 的 `ep` 参数是**列表索引**而非端点地址，`ep=1` → `0x83`/`0x04`
- `setTerminalEnable` 由两个包组成，第二个（AdjustControl `0x601/0x1f`）在 PMCA 中被 `try/except` 静默吞掉，**实际很可能失败**
- YuuLuo 的协议记录也提示：**部分查询命令无响应，调用会使端点进入异常状态**

**结论**：不要指望「进服务模式就能拿到 Linux shell」。这条在 FX30 上没通。

## 四、会话语义陷阱（最重要的一条）

### 服务模式会话**不可复用**

| 做法 | 结果 |
|---|---|
| 一次运行内「认证 → 操作 → 结束不 stop」（想留着会话下次用） | ❌ 下次重新认证时读超时：`reaping request failed, win error: 连接到系统的设备没有发挥作用` |
| 每次从 MSC 干净起步 | ✅ 稳定 |

**原因**：Jiritsu 会话有 `sequence`（从 1 递增）与设备句柄绑定，残留会话再认证即失效。

**正确节奏**：

```
相机 MSC 模式 → 一次运行内完成认证与全部操作 → 发 StopSenser → 断电/拔插回 MSC
```

### 退出后不会自动回 MSC

`StopSenser` 之后相机落到 **HID 模式（`054C:096F`, `svc=HidUsb`）**，`libusb`/PMCA 都识别不了。必须**拔插 Type-C**（通常即可）或取电池重启。

## 五、`0x60F` 区间会使端点异常

`0x60F` 的 `cmd 1/2/3` 三个命令均触发 `GenericUsbException`，之后端点状态不可靠。**扫描时应跳过该区间。**

## 六、`0x603` 的参数格式未解

`0x603 cmd1/2` 恒返回 `129`（命令存在、参数不对）。试过的 payload 全部无效：

```
（空）  u32(0)  u32(1)  ascii"0"  "/usr/lib/appFw.so\0"  "appFw.so\0"  16×0x00
```

即便 PMCA 的备份读取用 `dump32le(id)` 送 `id=0/1/2` 也是 `129`。

**结论**：`0x603` 的 cmd1/2 参数格式与 PMCA 的实现不一致，未解。但 `cmd5`（PDT_READ）**不需要参数**即可读全量备份，已足够。

## 七、驱动选择：必须 libusbK，且两个设备都要换

| 驱动 | 现象 |
|---|---|
| `libusb-win32`（`svc=libusb0`, v1.4.0.0） | 认证可过，但传输不稳；相机屏显「请检查所连接的设备」；`writeTerminal`/大批量读易超时 |
| **`libusbK`（`svc=libusbK`, v3.1.0.0）** | **稳定** |

**关键**：MSC 身份（`054C:0E0E`）与服务身份（`054C:0336`）是**两个独立设备**，**两个都要装 libusbK**。只换一个会导致服务模式下的传输失败。

PMCA 文档推荐 `libusb-win32` 是基于老机型时代的说明，BIONZ XR 机型应使用 `libusbK`。

---

## 八、「请检查所连接的设备」是预期现象

换成 libusbK 后，相机屏幕会显示「请检查所连接的设备 / 请检查 USB 连接设备」。

**这不是故障**——libusbK 是不主动应答的裸端口驱动，不像 USBSTOR 那样做 SCSI 轮询，相机等不到应答就会提示。**只要 USB 枚举仍为 `054C:0E0E`，就说明 MSC 模式还在，可以继续。**

---

## 九、扫描的时间陷阱

- 单次 `sendSenserPacket` 在命中大块数据时很慢（2.25 MB 一次）
- 96 组盲扫会超过 7 分钟上限；**必须 `python -u` 无缓冲**，否则被 SIGTERM 杀掉时输出全丢
- `0x611 cmd1` 每次返回 2 MB，扫到它要留足时间

## 十、驱动模式不在任何只读通道（实测，2026-10-21）

目标：定位「驱动模式（drive mode）」在机身中的读写位置，为启用连拍找入口。

### 1. 备份数据（PDT，`0x603/cmd5`）不含驱动模式

> **⚠️ 2026-10-24 补充（原因已查明）**：本节说「驱动模式不写入 PDT 备份」是对的，但当时归因错了。
> 真正原因是 **PDT 根本不是用户设置文件**——它是 `/setting/Backup.bin`，
> 而该文件是 `bk.elf` 从 **CP/MP 芯片**读出的参数备份（`bk g[ChipID] BackupID`）。
> 固件启动时不从这个文件恢复任何用户设置，所以改它必然无效。
> 详见 [`13-flash-layout.md`](13-flash-layout.md) §3。

做了四轮完整 dump，每轮均为 2,253,564 字节：

| 轮次 | 相机状态 |
|---|---|
| `single` | 驱动模式 = 单张拍摄 |
| `selftimer` | 驱动模式 = 自拍定时（单张）2s |
| `reboot` | 关机重启后（保持自拍定时） |
| `back` | 改回单张 + 关机重启 |

结果：

- `single` vs `selftimer`：**属性级 0 差异**。仅文件头 2 个字节变化（`0x20` 与 `0x2C`，均只改最低字节、都 +6，特征为计数器）
- 三方对比（`single` / `reboot` / `back`）筛选「`reboot` 偏离且 `back` 回退」的可逆属性：**0 个**
- 只有 12 个「只增不减」的计数器属性在变

**结论**：驱动模式不写入 PDT 备份。改设置既不会落盘，也不可能靠改备份属性来影响它。

### 2. 状态命令不反映驱动模式

对比两种驱动模式下 `0x604 cmd1-16` / `0x610 cmd1-3` / `0x603 cmd6/0x0F/0x10` 的返回值：

**22 行输出完全一致，零差异。**

这些命令返回的是稳定常量，例如：

| 命令 | 返回 | 特征 |
|---|---|---|
| `0x604/0x01` | `00` | 状态位 |
| `0x604/0x02` | `00460007` | 版本号形态 |
| `0x604/0x03` | `0001` | — |
| `0x604/0x06` | `000600` | — |
| `0x604/0x08` | `0000000d` | — |
| `0x604/0x09` | `003c000e` | — |
| `0x604/0x10` | `010000000000` | — |
| `0x610/0x02` | `02000000` | — |

**结论**：驱动模式是纯运行时状态。**没有任何只读命令能把它读出来**——连「确认当前值」都做不到。

### 3. 唯一能看见它的地方在固件里

据 A6700 研究者提供的线索：

```
names from area_check_data.dat    {u32 key, u32 id}
lib_appFw.so  .rodata  0x3664A70
```

`area_check_data.dat` 是一张 `{u32 key, u32 id}` 映射表（`key` 疑为设置项名称的哈希），嵌在 `lib_appFw.so` 的只读数据段，起始偏移 `0x3664A70`。

**要读到这张表，必须先拿到固件镜像**；而读文件的 `FileControl`（`0xff01`）与读内存的 `MemoryDump`（`0xff03`）在本机身上均返回 `128`（见本文第一、二节）。

### 4. 结论（已更新）

> **2026-10-23 更新**：官方固件已通过 `BODYDATA.DAT` + fwtool（PR #52）解出，`appFw.so` 已完成离线分析；本节原结论「只能靠 Pico 或他人提供映射表」**已不适用**。能力表与 `feature_id = 419`（`DRIVE_MODE_CONT_SHOOTING`）均已定位，见 [`08-appfw-capability-table.md`](08-appfw-capability-table.md)。

现在缺的不是分析资料，而是**写入通道**：

1. `0xff01` FileControl —— **待实机复测**（见第一节更正）
2. `pFunc=0x40 / category=0x1001` Jiritsu —— **待实机探测**（见 [`07-jiritsu-breakthrough.md`](07-jiritsu-breakthrough.md)）
3. 硬件路线（Pico / BootROM）—— 兜底

## 十一、`0x603/1`、`0x603/2` 无法按 ID 读写单个属性

试过的 payload 格式（**全部返回 129**）：

```
（空）
u32(1208) / u16(1208) / u64(1208)
u32(1208), u32(0)
u32(1208), u32(1)
u32(0), u32(1208)          ← ChipID 在前
u32(1), u32(1208)
u32(0), u32(1208), u32(4)
u8(0), u32(1208)
0x3E014D, 0x1B, 1208, 0        ← IPC 消息格式
0x3E014D, 0x1B, 1208
0x1B, 0x3E014D, 1208
0x014D, 0x1B, 1208             ← u16 模块 ID
1208, 0x3E014D, 0x1B
1208, 0, 0, ...（padding）
ASCII "1208"
"/usr/lib/appFw.so"
"appFw.so"
16 × 0x00
```

而 `0x603/5` 读全量备份（2,253,564 字节）**不需要任何参数，正常返回**。

> **⚠️ 2026-10-24 更正：本节结论不成立。**
>
> 上表 20 种 payload 里**唯独漏了最朴素的「裸 4 字节 id」**——不是 `u32(1208)` 加任何前缀/后缀，而是**只有 4 字节**：
>
> ```
> 0x603/1  payload = u32le id          → res=0，返回 4 字节值
> 0x603/2  payload = u32le id + data   → res=0
> ```
>
> 实测 `id=0x50000` 返回 `res=0` + 4 字节。有效 id 范围 `0x50000`–`0x505xx`（约 1024 条），`0x4FFFF` 及以下、`0x50800` 及以上均 129。
>
> 所以「FX30 没有按 ID 读写单个属性的通道」是**错误结论**，起因是扫描时只试了 5/8/12 字节对齐格式。
> 详见 [`10-setting-channel.md`](10-setting-channel.md) §7。
>
> **但这条通道对驱动模式仍然没用**——扫完 1024 条，单张 vs 自拍定时差分**值不同 0 条**。见本文 §十三。

## 十二、两个容易走错的方向

### `libInfraExtBackupCommunicator.so` 不是设置读写通道

看名字容易误判。它是**远程备份通信**（网络/无线传照片）。

- ExtCmd 模块 4 支持的命令只有 **`[1, 6, 7, 8, 9]`**（另有模式下 `1-5`）
- 命令表硬编码在 `.data` 段：`0x151D0 → [1]`、`0x151D8 → [1,2,3,4,5]`、`0x151E8 → [1,6,7,8,9]`、`0x151F8 → [1]`
- `(4,1) GetSupportedCommandIds` 的响应固定 8176 字节（`0x1FF0` 硬编码在 `0x2510: mov w0,#0x1ff0`）
- `ExtBackupCommunicator::ReadBackup(int,int,void*)` 是内部方法，无 `bl` 直接调用（经函数指针）

### `area_check_data.dat` 不是 BKID 映射表

实际路径 `/usr/share/app/area_check_data.dat`（固件内 `share/app/`），1,367,894 字节，魔数 `UXAC`。

内容是 **UI 字符串表**（条目里全是 `STRID_*`，如 `STRID_ALPNUM_12_V`），与 `BKID_*` 完全无关。搜索 `drive_mode_cont_shooting` 在该文件里 **0 命中**。

**真正的 BKID 表在 `appFw.so` 的 `.data.rel.ro` 段**，结构 `{u64 name_ptr, u32 id, u32 extra}`，见 [`05-firmware-analysis.md`](05-firmware-analysis.md)。

## 十四、`0x603/1` 的 1,024 条属性表与驱动模式零相关（实测）

`0x603/6` 的 status 返回 52 字节：`40 00 00 00 | fc 62 22 00`（= PDT size 2,253,052）+ ASCII **`CX96701_CN2`**。

用裸 4 字节 id 扫 `0x50000`–`0x503FF`（1,024 条）：

| 项 | 数量 |
|---|---|
| 总条目 | 1,024 |
| `res=0`（有效） | **825** |
| 返回 129（未注册） | 199 |
| 非零值 | 116 |

`res=0` 的 825 条与设置项注册表的 843 条数量接近，但**顺序不对应**：`0x50000 + 注册序号` 映射不成立（驱动模式那 12 条 `0x50123`–`0x5012E` 全为 0）。

### 差分结果

`--tag=single` 与 `--tag=timer` 两次全扫：

> **值不同 0 条。**

### 结论

这张属性表是**静态副本**，完全不反映运行时驱动模式。

## 十五、`0x8EF80` 当 ID 读 → 129（ID 不是 PDT 偏移）

假设「`0x603/1` 的 id 就是 PDT 文件偏移」，逐个试：

| 试的 id | 结果 |
|---|---|
| `0x8EF80` | **129** |
| `0x80000` | **`res=0`，返回 256 字节，全零** |
| `0x80080` | 129 |
| `0x7FFF0` | 129 |
| `0x14F` / `0x272` / `0x273` / `0x278` / `0x284` / `0x286` | **全 129** |

**结论**：`0x603/1` 的 id 空间与 PDT 文件偏移**无关**，也与设置项注册表 id（`0x272` 一族）**无关**。它是独立的内部句柄号。

（`0x80000` 返回 256 字节但全零，是唯一异常点，未解释。）

## 十六、跨构建「同 RVA ＝ 同代码」不成立（anchor 不可平移）

社区流传一种方法论：某机型在 `base+0x286CAA0` 找到 anchor，其他机型同址即视为同构、可照搬。

三机型同一 RVA 的 40 字节实测：

| 机型 | 内容 |
|---|---|
| FX30 | 一串 `ret` + `adrp/ldr/str` 属性访问器桩 |
| FX3 | `adrp x0,#0x821c000` / `mov x1,#0x96c4` / `add` / `add` / `ret` |
| A6700 | `mov w0,#-0x2f85` / `strh w0,[x29,#0x458]` … |

- `FX30 == FX3` → **False**
- `FX30 == A6700` → **False**
- FX30 那 40 字节的前 24 字节在 A6700 `.text` 里**搜不到**

`.data` 基址三家本就不同：FX30 `0x47D16E8` vs FX3 `0x47CD6E0`，差 `0x4008`。

**结论**：跨构建命中同一 RVA 是巧合概率问题，**不能作为同构证据**。照搬会写坏无关的 `.bss` 变量。

## 十七、三轮「找开关」全部为负：FX30 里没有缺项

这一节汇总三次独立的「缺项扫描」，结果全部为 0：

| 检验 | FX30 | FX3 | 结论 |
|---|---|---|---|
| `DRIVE_MODE` 大写常量集合差（FX30 独有） | **0 条** | **0 条** | 两者交集 419 条完全一致 |
| `AVAILABLE`/`LIMIT`/`ENABLE` 类常量（FX30 独有） | **0 条** | — | FX30/FX3 各 948，A6700 1142 |
| `.rodata` 里 `0x1A2 → 0x1A3` 连续序列（菜单列表） | **3 处** | **3 处** | 列表没漏掉连拍 |
| `cx96701`/`cx94701`/`cx89501` 型号串 | **0 命中** | **0 命中** | 机型识别不走字符串 |

再加上三条已有结论：

- 设置项注册表 843 条，FX30 / FX3 / A6700 **零差异**（同 ID 名称不同 0 条，双方独有 ID 0 条）
- `.dynsym`：FX30 **801** / FX3 **800**，**FX3 独有导出符号 0 个**
- FX30 的 `.text` 比 FX3 **大** 11,128 字节

⇒ **FX30 固件里连拍相关的每一个名字、每一条列表、每一个 API 都在，代码量还更大。**
不存在「功能缺失」或「模块没编进去」，只剩「运行时读某个值后分支」这一种解释。

## 二十、`0xff01` 的行为在三机型不一致（未解）

| 机型 | `0xff01` FileControl | 来源 |
|---|---|---|
| **FX30 6.00** | 全部返回 **128** | 本项目实测（`docs/07` §2 更正） |
| ZV-E10 | **可用于 `put`，任意路径** | ZVE-10-Camtool 文档 |

**这是目前最明确的一处机型差异**，三种可能：

1. Cinema Line 固件裁掉了这条通道（与早期推测同向，但早期那次是格式错误，不能作数）；
2. 调用格式不同 —— 对方走的是「先 `select(path)` 再写」的两段式，我们直接写；
3. 认证阶段差异 —— 需要更晚的阶段才开放。

**处置**：暂不改结论。凡是需要「往任意路径写文件」的动作，一律走 Jiritsu 命令，
不依赖 `0xff01`。等有空时按对方的 `select → write` 两段式在 FX30 上单独试一次。

## 二十一、`/tmp` 是持久分区，不是 tmpfs

ZV-E10 的实测：`/tmp` 挂的是 **nflasha10（12 MB）vfat**，重启不清。
FX30 上 `/tmp/jiritsu` 在 **nflasha6**，同理。

两条推论：

1. 测试载荷**必须显式删除**，不能指望断电清除；
2. **删掉 `libJit.so` 会让 Jiritsu 卸载整个 nflasha6** —— 此时读 `/tmp/jiritsu` 返回 **130**，
   要发 `0x4002`(MOUNT) 重新挂载才会恢复。

> 本项目早期把「返回 130」当成「文件不存在」，方向错了。130 是**分区已卸载**。
