# 10 · 设置通道：真实文件系统读写 + 设置区读写（实机验证）

> 2026-10-23 深夜 ~ 10-24 凌晨，FX30 (Ver.6.00) 实机完成。
> **不含固件二进制、不含完整设置快照。** 只给方法与结论。

---

## 一、真实根文件系统：任意读取（已验证）

### 结论

可以读取相机真实根文件系统上的任意文件。物证：

| 项 | 值 |
|---|---|
| 路径 | `/usr/lib/libJiritsu.so` |
| 返回 | `rc=0`，**233,416 字节** |
| 头部 | `7f 45 4c 46 02 01 01 00`（AArch64 ELF） |
| 相机内 SHA-256 | `563573d0…6f0f555b` |
| 固件解包 SHA-256 | `563573d0…6f0f555b` |
| 一致性 | **逐字节相同** |

顺带证明：机身固件与官方固件包为同一版本，无版本漂移。

### 三条铁律

**1) 必须用 `arg0 = 0` 分支**

`category=0x1001 / cmd=0x4011`（`GET_FILE2`）的 `arg0` 决定路径基址：

| arg0 | base | 能否穿越 |
|---|---|---|
| `1` | `/mnt`（media 抽象，SD 卡） | ❌ 根钳制，`..` 到顶即停 |
| **`0`** | **`/tmp/jiritsu`（`sys_mount("/dev/nflasha6")` 真实挂载）** | ✅ 可穿出 |
| `0xFF` | 预上传内存槽 | 不涉及文件系统 |

**2) 路径需加 `/../../` 前缀**

```
SET_FILE_PATH(cmd 0x400F)  payload = [0x00] + "/../../etc/hostname\0"
GET_FILE2    (cmd 0x4011)  payload = [0x00, 0xFF, 0x00]
```

**3) `GET_FILE2` 是一次性的**

反汇编 `adj_cmd_get_file2` 尾部：

```asm
0xA310  ldr  x0, [x19, #0x7e0]   ; 全局：SET_FILE_PATH 存下的路径
0xA318  bl   free                 ; 无条件 free
0xA31C  str  xzr, [x19, #0x7e0]   ; 并置 NULL
```

每次调用结束都会销毁路径。**每次读之前必须重新 `SET_FILE_PATH`**，否则返回 `0x10000201`。

### 负结果：media 沙箱不可穿越

`arg0=1` 时 `..` 本身被正常解析，但无法越过 media 根：

| 路径 | 结果 |
|---|---|
| `/PRIVATE/M4ROOT/CLIP/../CLIP/<f>.XML` | ✅ 读到 |
| `/PRIVATE/M4ROOT/CLIP/../../../../etc/os-release` | ❌ 不存在 |
| `/../mnt/PRIVATE/SONY/SONYCARD.IND` | ❌ 不存在（同一文件去掉 `..` 就能读） |

## 二、错误码速查（由固件日志串证实）

| 码 | 日志串 | 含义 |
|---|---|---|
| `0x10000004` | — | mount 失败 |
| `0x10000006` | `adj_cmd_get_file: file non-existent` | **文件不存在** |
| `0x10000008` | `adj_cmd_get_file: open err` | **存在但打不开** |
| `0x1000000A` | `adj_cmd_get_file: write err fd_mem` | 回写失败；**传目录时会出现，可作"目录存在"判据** |
| `0x1000000F` | `set file path len over` | 路径过长 |
| `0x10000201` | — | 参数错误（多半是路径已被消耗） |

`0x6 / 0x8 / 0xA` 三者组合起来，可以在不读内容的前提下判断
「不存在 / 是文件 / 是目录」。

## 三、`0x603`（AdjustControl）命令表：正确的载荷格式

早期扫描漏掉了一种关键格式，导致「单条读写全部 129」。实际格式如下：

| cmd | 功能 | payload |
|---|---|---|
| `1` | **read(id)** | `u32le id` |
| `2` | write(id, data) | `u32le id + data` |
| `3` | save(subsystem) | `u16le` |
| `4` | PDT write | `u32le protectMode + 全量数据` |
| `5` | PDT read | `u8 (1 = fromMemory)` |
| `6` | PDT status | 空 |
| `15` | backup id1 | `u8` |

### 早期为什么全 129

当时只试了 5 / 8 / 12 字节的组合（`chip+id`），**唯独没试裸的 4 字节 id**。
用 `u32le id` 后：

- `id = 0x50000` → `res=0`，返回 4 字节 → **格式正确**
- `id = 1206…1212`、`id = 1` → `res=129`

**说明 `BKID_xxx` 与 backup id 是两套编号**，有效 id 在 `0x50000` 一族。
（`BKID_` 从命名看像 Backup Key ID，但实测不成立，此命名关系不成立。）

## 四、关键发现：`0x603/5` 的 `fromMemory` 标志

`0x603/5` 的 payload 决定数据源：

```
payload = b""      ≡ b"\x00"   -> fromMemory = 0（闪存预设）
payload = b"\x01"              -> fromMemory = 1（内存实时值）
```

实测（同一会话连读三次）：

| 读取 | 长度 | 与 mem0 的差异 |
|---|---|---|
| `b""` | 2,253,564 | — |
| `b"\x00"` | 2,253,564 | **0 字节（完全等同）** |
| `b"\x01"` | 2,253,564 | **1,309 字节** |

**空 payload 等价于 `fromMemory=0`。** 早期所有快照都用了空 payload，
因此拿到的一直是「闪存预设」，看不到实时状态——这是此前多次差分失败的根因。

典型差异：某 579 字节区间内，`mem0` 保留历史字符串（如设备名、日志），`mem1` 全 0。

## 五、驱动模式字节的定位（mem1 模式差分）

方法：`0x603/5` + `b"\x01"`，在不同驱动模式下各采一份 2.25 MB，逐字节 diff。

### 结果：三种模式

| 模式 | `0x08EF80` | `0x091690` |
|---|---|---|
| 单张拍摄 | `00` | `00` |
| 单拍阶段曝光 | `02` | `09` |
| 自拍定时 | `08` | `05` |

三份快照之间，除计数器外只有这两处 + 少量计数器差异
（单张↔定时共 10 字节 / 7 处）。

- **`0x08EF80`**：随驱动模式变化 → 驱动模式相关值
- **`0x091690`**：也随模式变化，但取值更像「该模式的参数」（如自拍秒数、阶段曝光张数）

### 与外部线索的交叉验证

该偏移与另一位研究者公开标注的「userblock 状态 `0x08EF80`」**完全重合**，
两条独立路径在同一偏移会合。

### 值语义仍未确定

三个已知值 `0x00 / 0x02 / 0x08` 不符合线性关系（若按功能 ID 线性映射，
单拍阶段曝光应为 `0x14`，实测 `0x02`）。也不像密集位标志（`0x02` 与 `0x08` 之间空着 `0x04`）。

**连拍对应的值尚未确定。**

## 六、设置区写入：通路已打通（实机验证）

### 方法：全量写回，不解析容器格式

设置快照的容器结构（6 字节 `{u32 id, u16 size}` 索引 + 数据区）尚未完整解出，
但**不需要解析它**——用 PDT 全量写入即可：

```python
# 1. 读 mem1
blob = send(0x603, 5, b"\x01")

# 2. 需要改哪个偏移就直接改
blob[0x8EF80] = value

# 3. 全量写回 + 保存
send(0x603, 4, u32le(protectMode) + blob)
send(0x603, 3, u16le(subsystem))
```

### 实机结果：原样写回测试（语义零改变）

```
0x603/4  写 2,253,568 字节  ->  res=0    耗时 2.2 s
0x603/3  save(subsystem=0)  ->  res=0
再读比对：差异 9 字节，全部是计数器
```

**`protectMode = 0`、`subsystem = 0` 可用；2.25 MB 写入被完整接受。**

### 单字节改写测试

```
0x8EF80: 0x02 -> 0x01   （写入 res=0，save res=0）
读回验证：0x01 已生效
断电重启后再读：0x00     ← 被固件归一化
```

**结论：该字节受固件校验，写入非法值会在启动时被归一到合法值（单张 = `0x00`）。**

这排除了「随便写个值就能强制切模式」的可能，也说明它并非无校验的裸状态。
