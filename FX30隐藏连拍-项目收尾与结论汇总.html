一、一句话结论

FX30 的隐藏连拍模式已经可以永久开启 —— 写设置区两个字节，拔电池冷启动一次即可。
它是无损、可逆、近乎永久的；唯一剩下的问题是不显示在菜单里，因此无法在菜单中切换、也调不了速度档。

python probe_drive_write.py --burst     # 开启连拍
# → 拔电池 ≥30 秒冷启动 → 相机进入连拍，能正常连拍

python probe_drive_write.py --single    # 回滚单张
python probe_drive_write.py --probe     # 只看状态，不写

二、连拍方案（配方与验证）

2.1 配方

偏移写入值含义
0x8EF800x01EXTERN_VAL_DRIVE_MODE 表 idx1 = BURST（外层菜单枚举）
0x916900x01DRIVE_MODE 表 idx1 = CONT_SHOOTING（内层驱动枚举）
必须成对写入。只写一个，固件发现不一致会回退 —— 这是本项目踩过的最大坑， 早期「写了没生效」的负结论就是这么来的。

2.2 三次独立复现（含失败与成功的直接对照）

#时间beforeafter结果

唯一变量就是「第二个字段有没有跟上」⇒ 成对写入的必要性由直接 A/B 对照确证。

三、底层机制

3.1 这两个偏移存的不是属性 id，而是枚举表位置索引

这是本项目最大的认知修正。固件 .data.rel.ro 有两张 16 字节/项的枚举表（{char* name; u32 id; u16 code}）：

偏移枚举表表基 vaddr0x000x010x020x050x080x0C
0x8EF80EXTERN_VAL_DRIVE_MODE_*0x41A0550 SINGLEBURSTBRACKETRAW_BURSTSINGLE_SELF_2SSINGLE_SELF_5S
0x91690DRIVE_MODE_*0x41A28F0 1_IMAGE_SHOOTINGCONT_SHOOTINGCONT_SHOOTING_LIMITEDSELF_TIMERCONT_BRACKETDRO_ADV_BRACKET

验证强度：12 份带标签快照 100% 自洽；27 份全量快照取值集合（0x8EF80 ∈ {0,1,2,8,12}，0x91690 ∈ {0,5,9}）全部落在表索引范围内。

此前「连拍候选值是 0x01/0x04/0x10」是按 id 猜的；按 索引 就是 0x01。

四、持久性边界（全部实测）

阶段操作结果
首次生效关机再开机（热重启）❌ 不生效
拔电池 ≥30 秒冷启动✅ 生效
已生效后关机再开机（热重启）✅ 保持
拔电池冷启动✅ 保持
进菜单浏览 / 切视频模式录视频✅ 保持
手动修改驱动模式设置❌ 掉回单张
一句话：写入后需要一次冷启动让固件加载；加载之后热重启不会清除。
只要不去手动改驱动模式设置，连拍近乎永久保持。
掉回时固件会把 0x8EF80 和 0x91690 都写回 0x00（已由 --probe 快照确认）。 掉了重新跑一次 --burst 即可。

六、菜单问题的五条探索路线

路线 1 · PDT 可变字段筛选 未走通

方法：m0/m1 双读一致性（噪声在 m0/m1 间必然不同）+ 三模式间有差异。
结果：PDT 里真正的「模式字段」只有 4 个（0x8EF80、0x91690、0x99688/89），没有菜单列表。

方法论漏洞：菜单显示列表是常量（三种模式下都一样），差分法筛不到常量字段。

路线 2 · PDT 常量字段搜索 未走通

条件：值域 ⊆ 0..16 的连续块 + 全快照恒定。
结果：宽条件 122,503 个候选，严条件仍 118 个，判据不足，无法收敛。

路线 3 · 固件侧菜单构造代码 未走通

在 0x015BFB44 找到菜单项构造代码（mov w0,#0xc30..0xc33 + 字符串 adrp #0x2faf000 + 0x373/0x395/0x3b7/0x3d9）， 但 dump 字符串后发现是 CMD_MULTI_FLASH_COMP_ALL_PLUS_2_5（闪光灯补偿），不是驱动模式。

教训：属性 id 空间在不同上下文会复用 —— 0x0C30 在 BKID 表是 registration_drive_mode0，此处却配闪光灯补偿。不能只看 id 数字认定语义。

路线 4 · 跨机型出厂备份对比 对齐成功

用 -560 对齐后，142 个差异字节 / 37 个字段。其中 84 字节构成 12 个「7 字节等值组」：

疑点：三组最强候选都是「FX30 全 0 / FX3 全 1」，不是混合值。 若真是「7 个模式的可见性」，则 FX30 连单张都不可见 —— 与事实矛盾。 ⇒ 形状像 ≠ 就是它。

路线 5 · B 方案：载荷注入 + .bss 读写 首次打通

这是今晚技术上最大的突破：载荷与 appFw 跑在同一进程，直接读写它的内存。

5.1 载荷所在进程

cmdline = /usr/bin/im.elf debug s g r u l i a lazy-global

5.4 写入测试：0x8220844/845 无效

写入 0x8220844=1、0x8220845=1 → 读回 01 01 确认生效、相机未崩溃， 但用户反馈菜单无变化（退出菜单重进也无变化）。

⇒ 0x8220844/845 不是菜单可见性开关，该靶点排除。

路径为什么排除

八、当前判断与下一步

8.1 我的判断

「可用」≠「显示」。连拍在 available0 和 available1 两处都标记为可用， 但菜单不显示；写启用标志也无效。

⇒ 菜单列表很可能是静态硬编码的（在 .rodata 或 .uxc 资源里）， 不随 .bss 变化。如果是这样，改运行时内存永远没用 —— 不管写哪个字段。

8.2 下一步（两条线）

线内容可行性
A · 静态菜单列表找 UI 的菜单定义：appFw.so 的 .rodata，或 share/app/*.uxc（50 MB UI 资源）。目标是找到「驱动模式菜单项列表」并确认是否含连拍纯离线，已派给 TRAE（第五期任务 4）
B · 跨机型普查把 3 个「7 字节组」在 A6700 / A7C2 上普查。若它们也是 01 ⇒ 支持「能力位」假设，可直接写 PDT 验证纯离线，已派给 TRAE（第五期任务 1）

8.3 如果继续 B 方案（改内存）

还有两条未试的靶点，但优先级低于上面两条：

  • 扫描 .bss 里 available 附近区域，找形如 {0,1,2,8} 的模式索引数组
  • 读 /dev/stream2（64 MB 共享内存，appFw ↔ im.elf 的 IPC 通道），看菜单数据是否经它传递
关键未验证风险：菜单是否启动时缓存。若缓存，运行时改 .bss 永远看不到效果， 必须在数据被读取之前写入 —— 那要改注入时机，难度显著上升。 （用户已试「退出菜单再进」，无变化，倾向于「缓存」或「靶点不对」。）

十一、风险与红线

11.1 写入风险分级

操作风险可逆性
写 PDT 0x8EF80/0x91690低✅ --single 一键回滚，快照齐备
写 PDT 未知字段（0x91700 等）中✅ 快照回滚 / 恢复出厂
写 .bss（内存）中✅ 重启即恢复（不持久，风险天然可控）
改固件高❌ 项目红线，不做

11.2 红线（保持）

  • ❌ 不发 0x4003(FORMAT) / 0x4006(FIRMUP)
  • ❌ 不改固件分区（只写 /setting 设置区 / stdout 日志）
  • ❌ 不手写 0x08DC14 / 0x07A640 / 0x6E9DC（运行时噪声）
  • ❌ 两个会话不同时操作同一台相机
  • ✅ 每次写 PDT 前自动存完整快照（2.25 MB，带时间戳，永不覆盖）
  • ✅ 出错先停，不盲目重试写入

11.3 操作要点

首次生效必须拔电池 ≥30 秒冷启动（热重启不加载）
验证 .bss 写入绝不能重启（重启即丢，什么都看不到）
SDK 环境PATH 必须前置 tools/pmca-src（否则 pyusb 枚举出幽灵设备）
相机模式USB = 海量存储器；054C:0E0E 与 054C:0336 都要装 libusbK
非官方项目，与 Sony Corporation 无任何关联。固件逆向与设备修改存在变砖风险，可能使设备失去保修。
