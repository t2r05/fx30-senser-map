01

这一晚发生了什么

从「能不能开」到「为什么菜单不显示」，六个阶段。

02

怎么开启

一条命令，两个字节，一次冷启动。

python probe_drive_write.py --burst
# → 拔电池 ≥30 秒冷启动 → 相机进入连拍

python probe_drive_write.py --single    # 回滚单张
python probe_drive_write.py --probe     # 只看状态，不写
✓ 必须成对写入

0x8EF80 = 0x01（外层菜单枚举 BURST）+ 0x91690 = 0x01（内层驱动枚举 CONT_SHOOTING）。 只写一个，固件发现不一致会回退。

这不是推测：只写 0x8EF80=0x08 时相机仍是单张；成对写 0x01/0x01 就进连拍。 唯一的变量就是第二个字段有没有跟上。

03

为什么是这两个值

它们存的不是属性编号，而是枚举表里的「第几项」。

这是整个项目最大的认知修正。固件里有两张 16 字节一项的枚举表，这两个字节存的是表内位置索引：

⚠ 早期猜错过

之前按「属性 id」的思路猜候选值 0x01 / 0x04 / 0x10，全错。 按索引想就只有一个答案：0x01。

04

能保持多久

关键在于区分两个阶段：「加载」和「保持」。

✕ 我错过的两次

第一次：只写一个字段就断定「PDT 不是真值源」—— 其实是状态不完整。
第二次：以为热重启能生效，让你白试了一轮 —— 「已生效后的保持」不能外推成「首次能生效」。

05

菜单为什么不显示

三层里前两层都通了，卡在最后一层。

位图长这样

available0 = 6，二进制 0b00000110：

⚠ 据此我的判断变了

连拍在 available0 和 available1 两处都标记为可用，但菜单不显示；写启用标志也无效。 所以菜单列表很可能是静态硬编码的（在 .rodata 或 .uxc 资源里）， 不随运行时内存变化。

如果确实如此，改内存永远没用 —— 不管写哪个字段。

06

试过的五条路

四条没成，一条只成了一半 —— 但每条都排除了一个可能。

① 从 PDT 里找可变字段 未走通

用「m0/m1 双读一致性 + 三种模式间有差异」筛，结果只找到 4 个模式字段，没有菜单列表。

漏洞：菜单列表是常量，差分法根本筛不到常量。

② 搜 PDT 里的常量数组 未走通

条件放宽到「值域 ⊆ 0..16 的连续块」→ 12 万个候选；加严后仍 118 个，判据不足。

「符合形态」不等于「就是它」。

③ 找固件里的菜单构造代码 未走通

在 0x015BFB44 找到疑似菜单项构造，dump 字符串后发现配的是闪光灯补偿，不是驱动模式。

属性 id 空间在不同上下文会复用 —— 0x0C30 在另一处就配闪光灯。不能只看数字。

④ 跨机型出厂备份对比 对齐成功

FX30 与 FX3 的 PDT 位移是 −560，对齐后相同率 97–100%。 顺带解开了一个困扰很久的假象：0x91690 = 0x0C 不是差异，只是同偏移读把两个不同位置比到了一起。

对齐后得到 142 个差异字节，其中 84 字节构成 12 个「7 字节等值组」，最强 3 组是 FX30 全 00 / FX3 全 01。

疑点：全是 0 对全是 1，如果真是「7 个模式可见性」，FX30 连单张都不可见了 —— 与事实矛盾。所以形状像不等于就是它。

⑤ 注入载荷直接读写内存 技术打通

这是今晚技术上最大的突破：载荷和 appFw 跑在同一个进程里（/usr/bin/im.elf）， 内存可读可写，而且没有 ASLR（两次拔插基址都是 0x7F40544000）。

用它读到了全部靶点的真实值，也成功写入了启用标志 —— 但菜单没变。

这条路的限制是：能改内存，改不了静态的菜单定义。

07

已经排除的路径

这些别再试了，每条都有实测依据。

只写 0x8EF80 一个字段固件回退，相机仍单张
用热重启验证写入首次生效不加载，必须冷启动
0x08DC14 / 0x07A640 当模式字段同一模式下有 9 个不同取值，是运行时噪声
0x603/1 读 BKID 属性BKID 族全部 res=129，该通道不服务它
zig 编译的 .so 载荷dlopen 返回 0 但 constructor 不执行 → 只能用 libssp 借壳
未对齐就比相同率delta=0 的 66.5% 是对齐前的数字，对齐后 97–100%
跨机型用同一偏移读0x91690=0x0C 是对齐假象
写 0x8220844 / 0x8220845写 1 后菜单无变化，已实测排除
改 available* 让菜单显示BURST 位本来就是 1，它已放行，不是瓶颈
08

下一步

方向从「改内存」转向「找静态菜单列表」。

→ 两条并行的线（都已派给外部执行方）

A · 找 UI 的菜单定义
在 appFw.so 的 .rodata，或 share/app/*.uxc（50 MB UI 资源）里， 找「驱动模式菜单项列表」，确认它到底含不含连拍。

B · 三个候选组跨机型普查
把 3 个「7 字节组」在 A6700 / A7C2 上也查一遍。 如果它们也是 01，就支持「能力位」假设，可以直接写 PDT 验证；如果是 00，候选证伪。

还有一个没验证的风险

菜单是否启动时就缓存好。如果缓存了，运行时改内存永远看不到效果， 必须在数据被读取之前写入 —— 那要改注入时机，难度会明显上升。

你试过「退出菜单再进」没有变化，所以倾向于「缓存」或「靶点不对」，二者之一。

必须记住的四个操作要点

1. 首次生效必须拔电池冷启动 —— 关机再开机不加载。

2. 验证内存写入绝不能重启 —— 重启即丢，什么都看不到。

3. 环境要先配 PATH —— 指向 tools/pmca-src，否则 pyusb 会枚举出幽灵设备。

4. 不要两个会话同时操作相机 —— 读数会互相污染。
